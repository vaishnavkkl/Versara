# PDF capability and integrity audit

Date: 2026-09-28. Scope: sections B-U and AX of the supplied professional-editor specification.

Implementation follow-up: [Native PDF integrity and reader search](../30-native-pdf-integrity-and-search.md) and [searchable OCR output](../33-ocr-and-image-preview-follow-up.md) record subsequent fixes and their limits. This audit below retains the original reviewed snapshot; its missing/risky entries must be read alongside those follow-ups.

This is a source-only audit of the current working tree, not a claim that outputs or gestures have been verified on a device. No connected-device commands, automated tests, builds, cloud processing, or dependency installation were used for this audit. No application code or UI was changed. Line references identify the reviewed snapshot and can move after subsequent edits.

Status meanings: **Implemented** means a specific capability has a complete source path; **Partial** means a working subset exists; **Missing** means no app workflow/native implementation was found; **Risky** means a concrete behavior conflicts with the requested contract or needs an integrity safeguard. None of these statuses substitutes for runtime validation.

## Existing architecture

- React Native owns routes, tool configuration, histories and file workflows. `src/features/pdf/pdf-tool-session.ts:7` lists the actual enabled tools; `src/constants/pdf-methods.ts:12` defines their catalog presentation. There are no camera-scanner, PDF redaction, PDF object-image editor, comment manager or AcroForm editor entries.
- Reading uses Android `PdfRenderer` (`modules/pdf-engine/android/src/main/java/expo/modules/pdfengine/PdfEngineView.kt:293`) and iOS `PDFView`/PDFKit (`modules/pdf-engine/ios/PdfEngineView.swift:17`). The Android view implements its own bitmap list, zoom and text-selection overlay; iOS delegates rendering/selection to PDFKit.
- Text editing, current drawing exports, shapes, signatures, page numbers and watermark exports use shared C++ PDFium. The routing distinction matters: `src/features/pdf/advanced-pdf-tool.tsx:139` chooses `editPdfText` whenever `nativeEditor` is true, and line 245 enables that path for all markup, watermark and numbering saves.
- Other transformations use Android PDFBox/Tesseract and iOS PDFKit/CoreGraphics/Vision in `PdfAdvancedTools`. Page organization is a separate `PdfOrganizer` worker. The older `PdfAdvancedTools` markup implementations remain present, but they are not the current markup UI's export path.
- The native drawing views sample touches and render live marks. JS receives a completed mark, holds the pending marks and passes normalized points back. Preview PNGs are bounded; original PDF contents remain the input to final text/markup exports.
- Worker cancellation, staging, output path restrictions, page/mark/point limits and resource disposal exist. They reduce identifiable risk but cannot establish frame-rate or memory guarantees from code alone.

## Integrity findings requiring priority

### High: signed documents can pass the page-organizer worker

`modules/pdf-engine/android/src/main/java/expo/modules/pdfengine/PdfOrganizer.kt:50` only checks encryption, assembly permissions and page count. `modules/pdf-engine/ios/PdfOrganizer.swift:58` has the equivalent checks. Neither inspects signature dictionaries/fields before modifying a document. Reorder/rotate then rewrite the source to a new output (`PdfOrganizer.kt:147`, `PdfOrganizer.swift:163`). Merge/extract/split also create rewritten documents.

This is a source-confirmed missing safeguard: signatures in resulting copies can be invalidated or lost. The original imported PDF is not overwritten by the native worker. It is nevertheless inconsistent with the explicit AX requirement and with guards already present in `TextEditor.cpp:489` and `PdfAdvancedTools.kt:64`. Inserted secondary PDF sources also lack a signature check (`PdfAdvancedTools.kt:181`, `PdfAdvancedTools.swift:185`). A shared, native preflight policy should cover every modifying input, including secondary inputs, before output creation.

The iOS advanced worker checks page widget fields of type `.signature` (`PdfAdvancedTools.swift:93`), whereas PDFium checks signature count and Android advanced uses PDFBox signature dictionaries. These checks are not semantically identical: an empty iOS signature field can be rejected, while non-widget signature structures need a more complete common inspection path. No cryptographic validity validation was found.

### High: ordinary compression and iOS metadata removal discard PDF structure

Android Balanced/Smallest compression and Flatten create a new PDF containing one JPEG image per page (`PdfAdvancedTools.kt:146`). iOS does the same (`PdfAdvancedTools.swift:149`). This removes the original content object structure, editable annotations, searchable/selectable text, links and forms. The current UI explains the loss, but the supplied specification requires explicit flattened export instead of normal compression doing this.

iOS metadata removal avoids page rasterization but redraws visible page content and annotations into a new CoreGraphics document (`PdfAdvancedTools.swift:162`). Forms, links and annotations therefore lose their original interactive representation. Android instead clears document information and reachable metadata dictionaries (`PdfAdvancedTools.kt:189`). The iOS UI acknowledges this at `advanced-pdf-tool.tsx:354`; it remains a cross-platform integrity difference.

Recommended future behavior: preserve page objects for default compression and metadata removal. Any existing raster export should require an explicit flattened-output choice while retaining the currently supported operation as an intentional option. Do not silently remove the current feature or redesign the screen during the audit.

### High: some modifications remove input encryption without a separate decision

The C++ path accepts an `inputPassword`, requires `(FPDF_GetDocPermissions(doc) & 0x418) == 0x418` for `nativeEditor`, then saves with `FPDF_REMOVE_SECURITY` (`TextEditor.cpp:487`, `:554`) and verifies without a password. The checked mask contains modify, extract/copy and assemble permission bits. This path is used by drawing, shapes, signature, watermark and page numbering. Android advanced transformations set `isAllSecurityToBeRemoved = true` by default (`PdfAdvancedTools.kt:162`); Max-quality compression does so at line 147. Protect is the explicit exception.

This is not a claim that all restricted PDFs bypass authorization checks. Guards differ by path:

| Path | Current guard |
| --- | --- |
| Android reader copy-selection | C++ `action: selection` checks `FPDF_GetDocPermissions(doc) & 16` before returning glyphs (`TextEditor.cpp:465`). |
| Direct Add/Edit/Remove Text | Non-`nativeEditor` requests reject any security-handler revision other than `-1` (`TextEditor.cpp:488`), so these require an unencrypted copy. |
| PDFium markup/watermark/numbers | Required opening password is used when loading; modifying requests require mask `0x418` and zero signatures (`TextEditor.cpp:461`, `:487`). |
| Android advanced tools | Password is supplied to PDFBox; operations other than info/preview require `canModify`, `canExtractContent` and `canAssembleDocument`, plus no signature dictionaries (`PdfAdvancedTools.kt:55`, `:62`). |
| iOS advanced tools | A locked document must unlock; operations other than info/preview require document changes, copying and assembly plus the signature-widget scan (`PdfAdvancedTools.swift:85`, `:91`). |
| Both organizers | Reject encrypted/locked input and require assembly permission; missing signature check remains a separate issue (`PdfOrganizer.kt:52`, `PdfOrganizer.swift:64`). |

Advanced OCR/text extraction are therefore more restrictive than a pure copy-permission check: they also require modification/assembly and reject signature-bearing input. Read-only PDFium preview can bypass modification/signature checks only when it has no commands and does not request editable object discovery (`TextEditor.cpp:485`).

Consequently, an authorized modification of an encrypted input can create an unencrypted output without an explicit “remove password” operation. Original bytes remain unchanged, but exported-file confidentiality changes. Raster output is inherently a new unencrypted PDF unless protection is deliberately reapplied. iOS PDFKit writes without explicit password preservation options in ordinary rewrite branches; preservation must not be assumed. Compression's original-byte fallback can retain encryption, so output security can also vary depending on whether the candidate shrinks.

Recommend native preflight/results fields for encryption and signature state, an explicit output-security policy, and validation that the resulting policy matches the request. Do not add a paid security SDK.

### Medium: drawing persistence is vector content rather than editable annotations

`advanced-pdf-tool.tsx:245` converts marks to `kind: 'mark'` commands. `TextEditor.cpp:237` creates a page path, and line 290 inserts it using `FPDFPage_InsertObject`. No current annotation object, `/InkList`, `/QuadPoints`, persistent annotation identifier, comment metadata or annotation re-import is created.

This preserves vector appearance and avoids rasterizing a PDF for basic drawing. It does not meet C/E/F/AX's editable-annotation contract. Current session IDs and transform handles do not survive a reopen as editor objects. The older iOS `PdfAdvancedTools.addMarks` function creates PDFKit annotations (`PdfAdvancedTools.swift:269`), but the enabled current UI export bypasses that function. It must not be counted as active cross-platform annotation support.

### Medium: Android image-to-PDF validation is weaker

Android commits a nonempty staged file at `ImagePdfConverter.kt:82` without reopening it and checking page count. iOS does reopen through `CGPDFDocument` at `ImagePdfConverter.swift:107`. Other PDF workers reopen/check page counts before commit, with repair additionally rendering pages. Add equivalent native validation to the Android converter before replacement/export claims are expanded.

Existing reopen/page-count checks do not prove that annotations, links, encryption, signatures, text or all visible content were preserved. Those require specific validators and later fixture verification.

### Medium: the Signature screen does not show its declared limitation

The visual-versus-digital distinction is correctly written in `guidance.sign` (`advanced-pdf-tool.tsx:42`). The markup branch returns at lines 333-351; `{guidance[tool]}` is rendered only in the later general-tools branch at line 354. The actual Signature screen therefore does not receive this explanatory text through that path. A compact existing-style caption would make the existing behavior clear without adding an unrelated workflow.

### Medium: drawing widths and behavior do not match the professional contract

The UI labels `Math.round(inkWidth * 1000)` as Thickness (`advanced-pdf-tool.tsx:343`), while PDF export uses a fraction of page width (`TextEditor.cpp:233`). This is neither points nor a consistent physical width across page sizes. Brush types primarily choose fixed width and opacity; pencil/marker/highlighter are not separate pressure or texture engines (`PdfMarkupView.kt:122`). No smoothing, multiply blend mode, pressure sampling, palm rejection or eraser implementation was found. Dotted strokes have explicit native geometry in the latest tree and a capability gate; code presence is not a visual verification result.

### Lower priority: image conversion resolution and markup geometry limits

Image-to-PDF uses at most 2200 pixels on the long edge plus a pixel budget on Android (`ImagePdfConverter.kt:107`); iOS uses a batch-dependent `min(3_000_000, 24_000_000 / count)` decode budget (`ImagePdfConverter.swift:77`). This deliberately bounds memory but means source image detail is not fully retained in final PDF output. A later full-resolution path needs streaming/embedding or an explicit resolution choice, not removal of memory bounds.

Watermark outline center/size is based on hard-coded page fractions (`advanced-pdf-tool.tsx:193`) while text is positioned by actual font bounds and a 36 pt margin (`:199`, `TextEditor.cpp:323`). The shape is decorative, not reliably a fitted enclosure around arbitrary watermark text. Existing text underline is an independent content path (`TextEditor.cpp:142`), so after saving/reopening it does not remain semantically attached to the text object.

## Native and free/offline dependency assessment

- Android native dependencies declared in `modules/pdf-engine/android/build.gradle:10` are PDFBox-Android 2.0.27.0 and Tesseract4Android 4.9.0. PDFium revision 8066, nlohmann/json and stb_image_write are bundled native dependencies with notices recorded in `modules/pdf-engine/THIRD_PARTY_NOTICES.md` and the vendored license files. This audit did not independently certify all transitive license terms.
- Apple PDFKit, CoreGraphics, ImageIO and Vision are system SDK frameworks, not an added commercial PDF product. They are not open-source implementations; they are system APIs available without a separate per-use document-processing fee. If the requirement is literally that every processing implementation be open source, the existing Apple framework usage does not meet that stricter interpretation.
- No paid PDF SDK, license-key check, account requirement, or runtime document-upload path was found in the PDF processing/viewing code reviewed. No cloud processing was used during this audit.
- Android OCR opens `tessdata/eng.traineddata` from application assets and copies it locally; it does not fetch a model at runtime (`PdfAdvancedTools.kt:130`). iOS invokes local Vision requests.
- Build/dependency preparation can use the network: `scripts/prepare-pdfium.mjs`, `scripts/prepare-pdf-ocr.mjs`, Maven/JitPack, and the podspec's preparation hook fetch native archives/models when missing. This is development-time dependency acquisition, not uploading user PDFs for cloud processing. None was invoked for this audit.
- Reuse the existing engines first. Bundled PDFium headers already expose annotation/form-related APIs, but header availability does not prove all required capabilities, coordinate transforms, security behavior or cross-platform exports are implemented. Secure redaction and content-preserving optimization need a separate native feasibility review before exposing controls. Do not route missing features to an online conversion service.

## Recommended implementation boundaries

1. Keep existing routes, `PdfPreviewToolbar`, `PdfPreviewStage`, `ColorSwatches`, text style controls, tool sheet and save flow. Extend the current tool implementations; avoid a second viewer/editor stack.
2. Establish one native document preflight/result contract: page count/geometry, encryption, permissions, signature presence, annotation support, editable text/image capabilities and expected export transformation. Use the same policy across PDFium, organizer and advanced workers.
3. Preserve source, command state, preview cache and final output as separate lifetimes. Extend the current edit/mark IDs into durable session records before adding autosave/recovery or cross-tool history. Existing PDF sessions and histories are memory-only (`pdf-tool-session.ts:10`, `use-mark-history.ts:6`, `pdf-text-editor.tsx:89`).
4. Introduce a versioned PDF edit-operation union rather than passing arbitrary new shape names through stringly typed branches. Record units explicitly: PDF points, normalized page coordinates, page crop box and rotation. Store annotation IDs, quads, geometry, style and semantic subtype separately from temporary rendered images.
5. Implement native editable annotation persistence and re-import first, then text-based highlighting, mark erase/delete/style changes and reusable presets. Expand capabilities without pretending existing vectors are already semantic annotations.
6. Implement scanner, OCR searchable layer, form values and image-object editing as distinct native capabilities behind the existing catalog/preview/workspace conventions. Leave unsupported controls unavailable until their full save/export paths exist.
7. Use reversible commands for pending page operations and expose existing reset/history affordances consistently. Export must materialize one snapshot and validate it before save-back; previews must never overwrite the source.

## Verification strategy within current permission

Current permission is code checks only. The root audit can run required lint/typecheck. This PDF audit itself only inspected source and wrote this document. Do not run connected-device automation, screenshots, test APK installs, automated tests, cloud builds, or cloud processing.

For a later implementation, static review should trace every enabled option from UI state through native serialization to final export, confirm matching Android/iOS capability constants, prove cancellation/teardown ownership, inspect bounded queues/caches and check staged output validation. Native compilation is useful only when separately within the user's permitted checks and with dependencies already available locally.

Future fixture/manual verification remains pending authorization. It should cover signed/encrypted documents, rotated/cropped pages, mixed page sizes, existing annotations/forms/links, font subsets/complex scripts, scanned pages, malformed inputs, cancellation/low storage, save-back recovery and output reopen. No source-only result should be described as verified visual correctness, 60 FPS, zero leaks, secure redaction, or preserved cryptographic signatures.
