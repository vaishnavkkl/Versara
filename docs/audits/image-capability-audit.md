# Image capability audit

Date: 2026-09-28. Scope: sections V-AN, AO-AR and AY of the supplied professional-editor specification. This is a source audit, not a visual, performance, device or automated-test result. No application code, UI, dependencies or cloud configuration was changed for this audit.

Implementation follow-ups: [editor foundation](../31-editor-functionality-implementation.md), [native color tools](../32-native-tone-curves-hsl.md), and [image preview navigation](../32-image-preview-navigation.md). The audit below retains the original reviewed snapshot; read its missing/risk entries with those later changes.

Status meanings: **Partial** = working foundations exist but the requested module is incomplete; **Missing** = no corresponding editor state, UI and native operation were found in the reviewed sources; **Risk** = a concrete source-level conflict with the requested behavior. An implemented route does not establish that every requested professional feature is implemented correctly.

## Architecture already present

- React Native owns tool configuration and navigation. Android bitmap/Canvas code and iOS Core Image/UIKit/ImageIO code perform image processing. The advanced image canvas reuses the native PDF markup view; this is a shared native drawing surface, not a cloud renderer.
- The main editor owns crop, rotation, flips, brightness, contrast, saturation, warmth, filter and resize state. `src/features/files/image-editor.tsx:25`, `:56`, `:151`.
- Advanced tools own processing parameters and use bounded, cancellable native image jobs. `src/features/files/advanced-image-tool.tsx:116`; `modules/file-engine/android/src/main/java/expo/modules/fileengine/ImageTools.kt:19`; `modules/file-engine/ios/ImageTools.swift:21`.
- Image text editing owns text commands and local undo/redo. OCR recognizes existing raster text; replacement covers it with sampled surrounding colors before drawing new text. The UI explicitly says that this works best on plain backgrounds. `src/features/files/image-text-editor.tsx:26`, `:55`, `:159`, `:294`; `modules/file-engine/android/src/main/java/expo/modules/fileengine/ImageText.kt:113`; `modules/file-engine/ios/ImageText.swift:114`.
- `ImageWorkspace` retains the original library file separately from the latest flattened temporary working image. Most inter-tool commits request PNG, avoiding an unnecessary JPEG encode at every switch; explicit compress/convert still uses the requested encoding. Only two working files are retained and the workspace is deleted after the last user releases it. `src/features/files/image-workspace.tsx:15`, `:25`, `:45`; `src/features/files/advanced-image-tool.tsx:258`.
- Mark history stores changed mark objects rather than bitmap copies, up to 40 actions. Image text history retains up to 30 command-list snapshots. There is no shared cross-tool command history or durable editor project/draft model. `src/features/pdf/use-mark-history.ts:4`; `src/features/files/image-text-editor.tsx:30`, `:159`.

## Concrete findings requiring priority

### I-01: Switching from the basic editor after an edit rejects the working output

**Risk, reproducible from the call contracts.** `ImageWorkspace.render` creates its destination under `Paths.cache` (`src/features/files/image-workspace.tsx:16`, `:37`). The basic editor passes this URI to `editImage` when applying changes before switching tools (`src/features/files/image-editor.tsx:151`). Android `ImageProcessing.export` requires the destination to be under `context.filesDir` (`modules/file-engine/android/src/main/java/expo/modules/fileengine/ImageProcessing.kt:137`), and iOS `ImageEditing.export` accepts only the Documents root (`modules/file-engine/ios/ImageEditing.swift:87`). Both reject the cache destination. Text and advanced exporters already accept both app-owned roots. This affects crop/rotate/adjust/filter/resize tool switching once changes need committing; it is not a request to remove the path safety checks.

### I-02: Final export does not preserve full source resolution

**Risk against AY.** The basic editor decodes the source with a maximum side of 3072 or 4096 pixels, and image text uses the same maximums. Advanced tools decode export inputs at 2048 or 3072 pixels and then enforce a 3 or 6 MP budget. This happens for normal exports, not only previews or explicit compression. Resizing the already reduced raster to requested dimensions cannot restore lost detail. Explicit dimensions above the budget are rejected, but non-resize exports can be reduced before saving.

Evidence: `modules/file-engine/android/src/main/java/expo/modules/fileengine/ImageProcessing.kt:144`; `modules/file-engine/ios/ImageEditing.swift:91`; `modules/file-engine/android/src/main/java/expo/modules/fileengine/ImageText.kt:124`; `modules/file-engine/ios/ImageText.swift:127`; `modules/file-engine/android/src/main/java/expo/modules/fileengine/ImageTools.kt:54`; `modules/file-engine/ios/ImageTools.swift:69`. The advanced tool discloses the 3-6 MP limit (`src/features/files/advanced-image-tool.tsx:282`), which is honest but does not satisfy full-resolution export.

### I-03: iOS image text export loses PNG transparency

**Risk and platform mismatch.** `modules/file-engine/ios/ImageText.swift:135` unconditionally sets `UIGraphicsImageRendererFormat.opaque = true`; final PNG selection at `:170` cannot recover the discarded alpha. The Android implementation edits an ARGB bitmap (`modules/file-engine/android/src/main/java/expo/modules/fileengine/ImageText.kt:124`). This also affects PNG working images when switching away from text editing.

### I-04: Advanced resize makes transparent pixels opaque

**Risk against AY.** Android fills the entire destination with the selected background before rendering, for fit, fill and stretch alike (`modules/file-engine/android/src/main/java/expo/modules/fileengine/ImageTools.kt:105`). iOS similarly composites the resized result over an opaque background (`modules/file-engine/ios/ImageTools.swift:117`). This means a transparent PNG can lose alpha in fill/stretch even though the background color control is shown only for fit (`src/features/files/advanced-image-tool.tsx:244`). An explicitly chosen canvas/background operation should remain distinct from an ordinary alpha-preserving resize.

### I-05: Cross-tool changes are flattened, not fully adjustable history

**Risk against V, AO and AY.** Switching tools exports the current result and replaces the route. The next route starts fresh local state against that raster. Original bytes are retained, but text, marks, filters and geometry from earlier tools are no longer editable objects. Workspace files and state disappear after release or process termination; there is no persisted command log, history cursor, autosaved project or crash recovery. PNG intermediates prevent typical cumulative JPEG loss, but they do not provide reversible editing or prevent repeated resampling. Explicit lossy compression/conversion is also baked before final export when switching tools.

Evidence: `src/features/files/image-workspace.tsx:25`, `:45`, `:69`; `src/features/files/image-editor.tsx:151`; `src/features/files/image-text-editor.tsx:197`; `src/features/files/advanced-image-tool.tsx:258`.

### I-06: Matching controls do not guarantee matching image results on both platforms

**Partial parity.** Main Android adjustments use color matrices while iOS uses Core Image filters. Brightness has different gain semantics; warmth uses red/blue channel scaling on Android versus `CITemperatureAndTint` on iOS. Mono/fade/cool also use distinct algorithms. Advanced Android blur is a box filter and sharpening a neighbor-based kernel; iOS uses `CIGaussianBlur` and `CISharpenLuminance`. This is real native processing, but pixel-equivalent results should not be claimed without a defined reference algorithm and fixture comparison.

Evidence: `modules/file-engine/android/src/main/java/expo/modules/fileengine/ImageProcessing.kt:89`; `modules/file-engine/ios/ImageEditing.swift:56`; `modules/file-engine/android/src/main/java/expo/modules/fileengine/ImageTools.kt:184`; `modules/file-engine/ios/ImageTools.swift:87`.

## Native and dependency assessment

- Existing image processing uses Android platform graphics APIs and Apple Core Image/UIKit/ImageIO. No paid image-processing SDK or image-processing service call was found in these processing paths.
- Android image OCR uses the bundled `com.google.mlkit:text-recognition:16.0.1` dependency (`modules/file-engine/android/build.gradle:23`); iOS uses Vision (`modules/file-engine/ios/ImageText.swift:29`). Bundling the Android recognizer supports offline inference in the inspected code. An on-device/free API is not the same claim as an open-source implementation; the audit does not certify ML Kit or Apple SDK code as open source.
- Android exposes JPG/PNG/WebP. iOS asks ImageIO which encoders exist and may expose HEIC/TIFF as well. This is explicit capability-based availability, not a reason to offer unavailable formats on Android.
- No new dependency is needed to fix the destination-root mismatch or preserve alpha. Full-resolution memory-safe export needs native bounded-region/tile or scanline rendering and encoding design; simply raising decode caps risks memory exhaustion.
- Future healing or segmentation must have a verified on-device implementation and redistributable free license. No remote service, paid SDK or cloud operation is proposed as a fallback.

## Recommended extension of the existing architecture

Keep existing routes, native views, bottom sheets, palettes and Save UI. Evolve `ImageWorkspace` behind those interfaces into a durable project containing immutable source references, normalized geometry, ordered editable operations/layers, a command journal/history cursor, preview cache records and export settings. Treat native output files as generated artifacts rather than the sole editable state. Preserve source, draft, preview and exported-output lifetimes separately.

Use a common operation contract with stable IDs and versioned parameters. Keep previews low-resolution and cancellable; replay the same operation graph from full-resolution sources for export, with a native tile/scanline budget. Keep geometry and masks in document coordinates. Make each user-committed operation one undoable command; coalesce slider/gesture updates into one action at completion. Persist commands and small metadata atomically, not a full bitmap for every slider tick.

The existing processors should grow shared semantics for adjustment ranges, color/alpha handling, crop coordinates, transforms and export policies. New controls should be enabled only when both their native operation and undo/export behavior exist. Layers, masks and selection must be modeled before adding controls that imply these features are already supported.

## Implementation order and affected files

1. Correct I-01 and I-03 without changing layouts: basic native export destination validation and iOS image text alpha handling. Define transparent-resize policy for I-04 while preserving explicit fit/canvas backgrounds.
2. Add full-source export planning and a common operation/history model behind the current UI; preserve existing route adapters. Main files: `image-workspace.tsx`, `image-editor.tsx`, `image-text-editor.tsx`, `advanced-image-tool.tsx`, native `ImageProcessing.kt`, `ImageEditing.swift`, `ImageText.kt/.swift`, `ImageTools.kt/.swift` and module contracts.
3. Add filter intensity, missing crop ratios, unified per-operation reset/history and documented parity semantics to the existing tools.
4. Introduce persistent text/shape/drawing layers and shared transforms, then selections/masks, selective adjustments and advanced color modules.
5. Add healing, clone, background segmentation and collage only after actual native offline capabilities and source-integrity behavior exist. No placeholder buttons or AI naming for simple cover/blur.

## Verification strategy and limits

The authorized verification for this task is source inspection and static checks. Lint/typecheck can validate TypeScript contracts but cannot prove native image fidelity, alpha preservation, gesture behavior, a frame-rate target or Android/iOS pixel parity. No device automation, screenshots, runtime profiling, automated tests or cloud operations were performed by this audit.

Code-review gates should trace every enabled UI action through its request contract, native implementation, cancellation/lifetime path and output encoding. Review path-root validation, explicit overwrite authorization, original preservation, max dimensions, alpha policy and metadata policy for each exporter. For future authorized verification, retain transparent PNGs, EXIF-oriented photos, wide-gamut sources, very large photos, cancellation cases, multipass edits and known image checksums as the fixture plan; automated/device execution remains deferred unless separately authorized.
